# Plan — HU-13 Pagar el pedido

Historia: `docs/historias/HU-13.md` · Issue #17 · Rama `feature/hu-13-pago`

Backend: el cobro de cada pedido, la conciliación que aplica lo que dice el
sistema de pago (pantalla, aviso y tarea de cada minuto), el vencimiento que
consulta antes, el pago tardío y el adaptador de Libélula traído del proyecto
de eventos (`proyecto tecno`). Frontend: en la página del pedido, «Pagar con
QR», el QR con la consulta sola, «Ya pagué», los botones del simulador y los
estados «Pagado» y «Pago a devolver».

**Dependencias nuevas (se avisa antes de instalarlas):** `com.google.zxing`
`core` y `javase` 3.5.3 en `pom.xml` (tarea 2, leer el QR que Libélula
entrega como imagen) y `qrcode-generator` 2.0.4 en el frontend (tarea 4,
dibujar el QR). Las mismas versiones que eventos.

## Tarea 1 — Cobro y estados nuevos del pedido · backend

**Archivos:** `entity/Cobro.java`, `entity/EstadoCobro.java`,
`repository/CobroRepository.java` (nuevos); `entity/EstadoPedido.java`,
`entity/Pedido.java`.

- `EstadoPedido` suma `PAGADO` y `PAGO_A_DEVOLVER` (columna de 15: entra).
- `Pedido` suma `pagado LocalDateTime` y:
  - `pagar(fecha)`: desde `PENDIENTE_PAGO`, `VENCIDO` o `CANCELADO` (el pago
    tardío revive); fija `pagado`.
  - `marcarPagoADevolver(fecha)`: solo desde `VENCIDO` o `CANCELADO`.
  - Cualquier otro paso, `IllegalStateException`; `cancelar` y `vencer` ya
    rechazan lo que no está pendiente (RF-5).
- `EstadoCobro { PENDIENTE, PAGADO, ERROR }`.
- `Cobro(idCobro, pedido ManyToOne, monto BigDecimal(12,2), referencia
  String(120) UNIQUE, codigoQr String(1000), urlPasarela String(255),
  estado, generado LocalDateTime, fechaPago LocalDateTime,
  consultadoSinPago LocalDateTime)`. Muchos por pedido: después de un error
  se genera otro (RF-6), pero **nunca dos `PENDIENTE` a la vez**, y uno solo
  puede quedar `PAGADO`, porque no se genera otro mientras haya uno pendiente
  ni con el pedido pagado.
  - `generar(pedido, CobroGenerado, ahora)`: el monto es el total del pedido,
    nunca uno del cliente.
  - `registrarPago(fecha)`, `registrarError()`: solo desde `PENDIENTE`.
  - `consultadoSinPago(ahora)`: la última vez que el sistema de pago dijo que
    no estaba pagado. Es lo que deja vencer el pedido (RF-7).
- `CobroRepository`:
  - `findFirstByPedido_IdPedidoAndEstado(id, PENDIENTE)`: el que se muestra
    y el que decide si el pedido vence. **Sin bloqueo:** se lee con el cliente
    ya bloqueado, y todo el que escribe un cobro bloquea antes al cliente. Un
    `FOR UPDATE` sobre los cobros de un pedido sin cobros bloquearía el hueco
    del índice (`decisiones.md` → «Pedidos»);
  - `findConBloqueoByIdCobro(id)`;
  - `datosParaConciliar(idCobro)` → `record CobroAConciliar(idCobro,
    referencia, idPedido, idUsuario)` solo si está `PENDIENTE`, sin cargar la
    entidad;
  - `idPorReferencia(referencia)`;
  - `idsPorConciliar(desde)`: los `PENDIENTE` generados desde `desde` (RF-8),
    ordenados por id.

**Lo delicado: generar el cobro.** Ninguna llamada al sistema de pago con
filas bloqueadas: dos transacciones cortas y la llamada en el medio, como en
eventos. Si otra pestaña guardó su cobro mientras tanto, gana ese y el
generado acá no se muestra nunca, así que nadie lo paga (RF-2):

```java
public PedidoResponse pagar(Long idUsuario, Long idPedido) {
	Preparacion preparacion = transaccion.execute(estado -> preparar(idUsuario, idPedido));
	if (preparacion.existente() != null) {
		return preparacion.existente(); // RF-2
	}
	CobroGenerado generado;
	try {
		generado = iPago.generarCobro(idPedido, preparacion.monto(), preparacion.concepto());
	} catch (SistemaDePagoNoDisponibleException error) {
		log.warn("No se pudo generar el cobro del pedido {}", idPedido, error);
		throw new CobroNoDisponibleException(); // RF-3: no se guardó nada
	}
	return transaccion.execute(estado -> guardar(idUsuario, idPedido, generado));
}

// Cliente y después pedido, como todo lo que cambia un pedido. Vence antes si ya era la hora
private Preparacion preparar(Long idUsuario, Long idPedido) {
	Pedido pedido = pedidoService.bloquearPendiente(idUsuario, idPedido); // 404 ajeno; 409 si no espera el pago
	Optional<Cobro> pendiente = cobroPendiente(idPedido);
	if (pendiente.isPresent()) {
		return Preparacion.existente(pedidoService.respuesta(pedido));
	}
	return Preparacion.nuevo(pedido.getTotal(), "Pedido N.º " + idPedido + " — " + marca);
}

private PedidoResponse guardar(Long idUsuario, Long idPedido, CobroGenerado generado) {
	Pedido pedido = pedidoService.bloquearPendiente(idUsuario, idPedido); // pudo vencer o cancelarse en la llamada
	if (cobroPendiente(idPedido).isEmpty()) {
		cobroRepository.save(Cobro.generar(pedido, generado, LocalDateTime.now(clock)));
	}
	return pedidoService.respuesta(pedido);
}
```

`bloquearPendiente` bloquea **primero** al cliente (antes de cualquier
lectura) y después el pedido, lo vence si corresponde (con la regla de RF-7,
abajo) y responde `PEDIDO_NO_PENDIENTE` si no espera el pago.

`cobroPendiente(idPedido)` es
`cobroRepository.findFirstByPedido_IdPedidoAndEstado(idPedido, PENDIENTE)`,
sin bloqueo. Los dos templates de `PagoService` y el de
`ConciliacionDePagos` van con `ISOLATION_READ_COMMITTED`, como en eventos:
cada lectura sin bloqueo ve lo último confirmado, y la segunda pestaña ve el
cobro que guardó la primera aunque algo se haya leído antes de bloquear al
cliente. Con REPEATABLE_READ, esa primera lectura fijaría la vista y
quedarían dos cobros pendientes (RF-2).

`marca` reutiliza `tienda.correo.marca` (`TIENDA_MARCA`), el nombre de la
tienda que ya usan los correos.

**Lo delicado: conciliar.** La única pieza que aplica un resultado: la usan
la consulta de la página, el aviso, la tarea de cada minuto y el
vencimiento. Consulta sin nada bloqueado y sin transacción abierta (una
llamada de 15 s no retiene una conexión); después bloquea en el orden de
siempre (cliente, pedido, cobro, productos por id) y vuelve a mirar el cobro
ya bloqueado: si otro lo procesó, no hace nada (RF-11). Devuelve si la
consulta respondió:

```java
public boolean conciliar(Long idCobro) {
	Optional<CobroAConciliar> datos = cobroRepository.datosParaConciliar(idCobro);
	if (datos.isEmpty()) {
		return true; // ya procesado
	}
	ResultadoDelCobro resultado;
	try {
		resultado = iPago.consultar(datos.get().referencia()); // RF-4: nunca lo que diga el cliente
	} catch (SistemaDePagoNoDisponibleException error) {
		log.warn("No se pudo consultar el cobro {}; se reintenta en la próxima vuelta", idCobro, error);
		return false; // RF-7: no vence
	}
	transaccion.executeWithoutResult(estado -> aplicar(datos.get(), resultado));
	return true;
}

private void aplicar(CobroAConciliar datos, ResultadoDelCobro resultado) {
	LocalDateTime ahora = LocalDateTime.now(clock);
	usuarioRepository.findConBloqueoByIdUsuario(datos.idUsuario()).orElseThrow();
	Pedido pedido = pedidoRepository.findConBloqueoByIdPedidoAndUsuario_IdUsuario(datos.idPedido(), datos.idUsuario())
			.orElseThrow();
	Cobro cobro = cobroRepository.findConBloqueoByIdCobro(datos.idCobro()).orElseThrow();
	if (cobro.getEstado() != EstadoCobro.PENDIENTE) {
		return; // RF-11
	}
	switch (resultado.estado()) {
		case PENDIENTE -> cobro.consultadoSinPago(ahora); // RF-7: ahora sí puede vencer
		case ERROR -> cobro.registrarError(); // RF-6: el pedido sigue igual
		case PAGADO -> {
			LocalDateTime fecha = resultado.fechaPago() == null ? ahora : resultado.fechaPago();
			cobro.registrarPago(fecha);
			if (pedido.getEstado() == EstadoPedido.PENDIENTE_PAGO) {
				pedido.pagar(fecha); // RF-5: la reserva queda como venta, sin movimiento
			} else {
				pedidoService.revivir(pedido, fecha, ahora); // RF-9: vencido o cancelado
			}
		}
	}
}
```

Un pedido pendiente que pasó la hora pero se paga queda «Pagado» aunque
todavía no se haya vencido: el pago llegó antes que el vencimiento (RF-7).

**Lo delicado: revivir (pago tardío, RF-9).** En `PedidoService`, con el
cliente y el pedido ya bloqueados:

```java
void revivir(Pedido pedido, LocalDateTime fechaPago, LocalDateTime ahora) {
	Map<Long, Producto> productos = new LinkedHashMap<>();
	for (LineaPedido linea : pedido.lineasPorProducto()) {
		productos.put(linea.getIdProducto(), bloquearProducto(linea.getIdProducto()));
	}
	// Todo o nada, como al confirmar: a la venta, con una cantidad que la unidad admite y con stock
	boolean alcanza = pedido.getLineas().stream().allMatch(linea -> {
		Producto producto = productos.get(linea.getIdProducto());
		return CarritoService.estado(producto, linea.getCantidad()) == EstadoLineaCarrito.DISPONIBLE
				&& linea.getCantidad().compareTo(producto.getStock()) <= 0;
	});
	if (!alcanza) {
		pedido.marcarPagoADevolver(ahora); // sin tocar stock ni carrito
		return;
	}
	for (LineaPedido linea : pedido.lineasPorProducto()) {
		Producto producto = productos.get(linea.getIdProducto());
		BigDecimal nuevo = producto.getStock().subtract(linea.getCantidad());
		producto.aplicarMovimiento(nuevo);
		movimientoRepository.save(MovimientoStock.reserva(producto, linea.getCantidad(), nuevo, pedido, ahora));
	}
	pedido.pagar(fechaPago);
	restarDelCarrito(pedido); // cada línea menos lo del pedido; en cero o menos, se borra
}
```

**Lo delicado: vencer con cobro (RF-7).** Un pedido vence solo si pasó la
hora **y** cada cobro pendiente tiene `consultadoSinPago >= vence`: el
sistema de pago dijo que no estaba pagado después de la hora. Lo revisa
`PedidoService` con el cliente y el pedido bloqueados, leyendo el cobro
pendiente sin bloqueo (`cobroPendiente`), en `vencer`, `vencerSiCorresponde`,
`confirmar` y `bloquearPendiente`. Una vista vieja solo puede ver el cobro
todavía pendiente o sin la última consulta: entonces no vence, que es lo
seguro, y la próxima vuelta lo resuelve. Quién consulta:

- `VencimientoPedidos.vencer()`: antes de vencer cada pedido, `conciliar`
  cada cobro pendiente; si alguno no respondió, ese pedido no vence en esta
  vuelta.
- La página del pedido, al llegar a cero con el QR a la vista, ya consulta
  (`/cobro/consulta`) y después pide el pedido otra vez.
- Las lecturas (carrito, pedido) no llaman al sistema de pago: un pedido que
  espera la consulta sigue «Pendiente de pago» con 0 segundos hasta la
  próxima vuelta de la tarea. `idDelPendiente` lo informa (pendiente con hora
  vencida y cobro sin consultar), y `confirmar` responde `PEDIDO_PENDIENTE`
  con su número.

`ConciliacionAutomaticaDePagos`: cada minuto, `conciliar` para
`idsPorConciliar(ahora - 24 h)`, cada uno en su transacción; uno que falla no
frena al resto (RF-8).

## Decisiones del plan

- **`Cobro` es una entidad aparte, no columnas del pedido:** después de un
  error se genera otro, y el historial de cobros queda para los reportes
  (HU-18).
- **`consultadoSinPago` en el cobro** decide si el pedido puede vencer, con
  todo bloqueado; así las lecturas no llaman al sistema de pago y el
  vencimiento no depende de cuándo se consultó.
- **Al pagar no se registra un movimiento:** la reserva ya restó el stock;
  solo el pago tardío, que vuelve a reservar, registra otra «Reserva por
  pedido».
- **Conciliar sin transacción abierta durante la llamada** (eventos la tenía
  abierta, sin bloqueos): una llamada de 15 s no retiene una conexión del
  pool.
- **Los cobros, sin `FOR UPDATE`, y READ_COMMITTED en lo del pago:** el
  bloqueo del cliente ya serializa todo lo que cambia un pedido y sus cobros,
  y un `FOR UPDATE` sin filas traba a otros clientes en MySQL.

### Distinto de lo planeado

- `Cobro.generar` recibe la referencia, el QR y la URL sueltos (no
  `CobroGenerado`): la entidad no depende del servicio.
- La conciliación corre cada minuto fijo con el interruptor
  `tienda.pago.conciliacion-programada`, como `VencimientoPedidos`, en vez
  de una propiedad de intervalo.
- `COBRO_NO_ENCONTRADO` (404) para simular sin cobro pendiente.
- El bloque del pago es un componente propio (`app-pago-del-pedido`) por el
  presupuesto de estilos, y su consulta de cada 5 s corre fuera de la zona
  de Angular (dentro, las pruebas no se estabilizaban).
- La página dice «Todavía no recibimos el pago» tras «Ya pagué» y «El pago no
  se pudo completar» tras un error.
- Revisiones: READ_COMMITTED en `PedidoService` y `CarritoService.ver`, dos
  hilos para las tareas, `LineaPedido.cantidadDevuelta`.
