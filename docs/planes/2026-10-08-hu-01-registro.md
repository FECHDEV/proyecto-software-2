# Plan — HU-01 Registro de clientes

Historia: `docs/historias/HU-01.md` · Issue #3 · Rama `feature/hu-01-registro`

El registro ya existe. Este plan hace tres cambios (sesión iniciada al
registrarse, límite por IP, «Crear cuenta» con sesión lleva al inicio) y pasa
las pruebas existentes a citar «HU-01 RF-N».

## Tarea 1 — Límite de registros por IP (RF-13) · backend

**Archivos:** `service/LimiteRegistros.java` (nuevo),
`exception/RegistrosExcedidosException.java` (nuevo), `UsuarioService`.

`LimiteDeFrecuencia` cuenta por correo e IP; el registro cuenta solo por IP, así
que la subclase usa una clave de correo fija. 5 en 1 hora, bloqueo de 1 hora.
Se cuenta **antes** de crear (operación atómica, una ráfaga no pasa del
máximo) y se **anula** si el registro no se completa (correo duplicado u otro
error), porque solo cuentan los exitosos.

```java
// Registros por IP (decisiones.md → Registro). LimiteDeFrecuencia cuenta por correo e IP: acá el correo es fijo
@Component
public class LimiteRegistros extends LimiteDeFrecuencia {

	private static final String TODOS = "";

	public LimiteRegistros(Clock clock) {
		super(clock, 5, Duration.ofHours(1), Duration.ofHours(1));
	}

	public void registrarIntento(String ip) { registrarIntento(TODOS, ip); }

	public void anularIntento(String ip) { anularIntento(TODOS, ip); }

	@Override
	protected ErrorNegocioException limiteExcedido() {
		return new RegistrosExcedidosException(); // 429 REGISTROS_EXCEDIDOS
	}
}
```

En `UsuarioService.registrarCliente`:

```java
limiteRegistros.registrarIntento(ip);
try {
	// ... lo de hoy: duplicado → CuentaExistenteException, saveAndFlush
} catch (RuntimeException e) {
	limiteRegistros.anularIntento(ip);
	throw e;
}
```

**Pruebas** (`LimiteRegistrosTest`, `UsuarioServiceTest`):
- `cincoRegistrosDesdeUnaIpBloqueanElSexto` — HU-01 RF-13
- `otraIpNoQuedaBloqueada` — HU-01 RF-13
- `pasadaLaHoraSePuedeVolverARegistrar` — HU-01 RF-13 (con `Clock` fijo)
- `correoDuplicadoNoCuentaParaElLimite` — HU-01 RF-13
- `registrosSimultaneosNoPasanDeCinco` — HU-01 RF-13 (hilos, como
  `peticionesSimultaneasNoComparanMasDeCincoContrasenas`)
- `limiteExcedidoNoCreaLaCuenta` — HU-01 RF-13
- `traduce REGISTROS_EXCEDIDOS` (`mensajes-error.spec.ts`) — HU-01 RF-13

## Tarea 2 — El registro devuelve la sesión (RF-2) · backend

**Archivos:** `UsuarioService`, `AuthController`.

- `UsuarioService.registrarCliente(RegistroClienteRequest, String ip)` pasa a
  devolver `SesionIniciada` (usuario + `tokenJwt.emitir(usuario)`), igual que

## Decisiones

- Clave de correo fija en `LimiteRegistros` en vez de generalizar
  `LimiteDeFrecuencia`: una línea, sin tocar los dos límites que ya funcionan.
- Se reutiliza `InicioSesionResponse` para el registro: es la misma sesión y el
  frontend ya sabe guardarla.
- El 429 lleva su propio código (`REGISTROS_EXCEDIDOS`) para que el frontend
  muestre un mensaje propio («Se crearon demasiadas cuentas desde esta
  conexión. Prueba de nuevo en una hora.»), que se agrega a `mensajes-error.ts`
  con su prueba (Tarea 1).

### Revisiones

- **`/security-review`:** sin vulnerabilidades. El token se emite solo para la
  cuenta recién creada (Cliente, activa) y el destino pasa por `destinoInterno`.
- **`/code-review`:** 8 hallazgos.
  - Corregidos: RF-13 decía «hasta que pase la hora» y el bloqueo es de una
    hora desde la quinta, como el del inicio de sesión (se precisó la redacción
    en la historia y en `decisiones.md`); un comentario huérfano de
    `correoDeAlta`; un comentario entre `@Transactional` y su método.
  - Descartados: (1) dos registros simultáneos justo en la quinta cuenta: el
    segundo puede recibir 429 aunque el primero falle — ventana de
    milisegundos, igual que el límite del inicio de sesión; (2)
    `anularIntento` quita el último instante y no el propio — comportamiento
    previo de `LimiteDeFrecuencia`, diferencia de milisegundos; (3) un fallo en
    el commit deja el intento contado — `saveAndFlush` adelanta los errores de
    datos, solo quedaría una caída de la conexión en el commit; (4) con `ng
    serve` todo llega desde 127.0.0.1 — solo en desarrollo: Docker y la nube
    usan el perfil `prod`, con la IP real; (5) `UsuarioService` emite el token
    como `AutenticacionService` — es la misma línea sobre `tokenJwt.emitir`.
- **`web-design-guidelines`:** sin hallazgos nuevos (la historia no cambió el
  HTML). Previo: los campos no tienen `name`, que ayuda a los gestores de
  contraseñas; queda para el chore del sistema de diseño (#8).
