# HU-15 — Subir el modelo 3D de un producto

**Como** administrador, **quiero** subir el modelo 3D de un producto, **para**
que los clientes lo vean en 3D.

Issue: #19

## Contexto

Un producto de la ferretería tiene hasta cinco fotos (HU-07). Esta historia le
suma un modelo 3D opcional, hecho fuera de la aplicación, que el
Administrador sube, revisa en un visor, reemplaza o quita cuando quiera. El
visor del detalle para los clientes, con la realidad aumentada, es HU-16.

Fuentes: issue #19; `decisiones.md` → «Rubro: ferretería, con vista 3D»,
«Visor 3D y modelos» (spike #14: `<model-viewer>`, `.glb`, 3 MB, menos de 1 MB
recomendado), «Imágenes subidas», «Productos» y «Catálogo de demostración»;
`CLAUDE.md` → «Tienda» y «Usuarios y roles»; HU-07.

Decisiones de la entrevista del 22/10/2026 (en `decisiones.md` → «Visor 3D y
modelos»):

- **Subir, reemplazar y quitar** un solo modelo `.glb` por producto; el
  archivo anterior se borra.
- **Vista previa con el mismo visor** (`<model-viewer>`) en el formulario del
  producto.
- **Entre 1 y 3 MB se acepta con un aviso** de que puede tardar en cargar.
- **Marca «3D»** en la lista «Productos» del Administrador.
- **El catálogo de demostración carga la columna `modelo_3d`.**

## Requisitos funcionales (EARS)

### Carga

- RF-1: EL SISTEMA deja subir, reemplazar y quitar el modelo de un producto
  solo al Administrador; a otro rol responde 403 y, sin sesión, 401.
- RF-2: CUANDO el Administrador sube un modelo a un producto (activo o
  inactivo), EL SISTEMA lo guarda con un nombre generado por el sistema y
  responde con el producto, que indica que tiene modelo y su tamaño.
- RF-3: SI el archivo no es un glTF binario versión 2 por su contenido (sin
  importar la extensión ni el tipo que declara el navegador), ENTONCES EL
  SISTEMA lo rechaza con 400 `MODELO_INVALIDO`.
- RF-4: SI el archivo pasa de 3 MB, ENTONCES EL SISTEMA lo rechaza con 400
  `MODELO_DEMASIADO_GRANDE`, también cuando el archivo es mucho más grande.
- RF-5: CUANDO el Administrador sube un modelo a un producto que ya tenía
  uno, EL SISTEMA lo reemplaza y borra el archivo anterior.
- RF-6: CUANDO el Administrador quita el modelo, EL SISTEMA borra el archivo
  y el producto queda sin modelo; si no tenía, no cambia nada.
- RF-7: SI el producto no existe, ENTONCES EL SISTEMA responde 404
  `PRODUCTO_NO_ENCONTRADO`, como en HU-07.

### Entrega

- RF-8: EL SISTEMA sirve el modelo de un producto con el tipo
  `model/gltf-binary`, por el producto al que pertenece, como las imágenes;
  un modelo que no es del producto, o que ya se reemplazó, da 404.

### Pantalla del Administrador

- RF-9: CUANDO el Administrador edita un producto, EL SISTEMA muestra la
  sección «Modelo 3D»: sin modelo, el botón para subirlo; con modelo, el
  visor (`<model-viewer>`) para girarlo, acercarlo y moverlo, su tamaño y
  los botones «Reemplazar» y «Quitar».
- RF-10: SI el modelo subido pesa más de 1 MB, ENTONCES EL SISTEMA lo guarda
  y avisa: «El modelo pesa 2,40 MB: en un celular con datos puede tardar en
  cargar. Lo recomendado es menos de 1 MB.».
- RF-11: MIENTRAS sube el modelo, EL SISTEMA lo indica y no deja subir otro;
  SI falla, ENTONCES muestra el motivo (formato, tamaño, conexión) y deja
  volver a intentar. Quitar pide confirmación.
- RF-12: EL SISTEMA marca con «3D» en la lista «Productos» del
  Administrador los productos que tienen modelo.

### Demostración

- RF-13: CUANDO el catálogo de demostración trae un archivo en `modelo_3d`,
  EL SISTEMA lo carga con las reglas de RF-2 a RF-4; SI no existe en la
  carpeta o no las cumple, ENTONCES la fila es inválida y no se carga nada,
  como con una imagen.

## Escenarios

### Sube el modelo (RF-2, RF-9)
- **Dado** «Martillo de peña» sin modelo
- **Cuando** el Administrador sube `martillo.glb` (0,40 MB)
- **Entonces** ve el martillo en el visor, puede girarlo y la lista lo marca
  con «3D»

### Modelo pesado (RF-10)
- **Dado** un producto sin modelo
- **Cuando** sube uno de 2,4 MB
- **Entonces** queda guardado y se le avisa que lo recomendado es menos de
  1 MB

### Archivo equivocado (RF-3, RF-4)
- **Dado** un producto
- **Cuando** sube una foto renombrada a `.glb`, o un modelo de 5 MB
- **Entonces** se rechaza con el motivo y el producto queda como estaba

### Lo reemplaza (RF-5)
- **Dado** un producto con modelo
- **Cuando** sube otro
- **Entonces** el visor muestra el nuevo y el archivo anterior ya no existe

### Lo quita (RF-6, RF-11)
- **Dado** un producto con modelo
- **Cuando** elige «Quitar» y lo confirma
- **Entonces** el producto queda sin modelo y sin la marca «3D»

### Demostración (RF-13)
- **Dado** `catalogo.csv` con `martillo.glb` en `modelo_3d`
- **Cuando** arranca la tienda con la base vacía
- **Entonces** el martillo queda con su modelo

## Casos límite

- **Un `.gltf` de texto, un glTF versión 1 o un archivo vacío:** se rechazan
  con `MODELO_INVALIDO` (RF-3).
- **Un modelo de exactamente 3 MB:** se acepta; uno de 3 MB y un byte, no
  (RF-4).
- **Un archivo de 30 MB desde la pantalla:** se rechaza en el navegador con el
  mismo mensaje que `MODELO_DEMASIADO_GRANDE`, sin subirlo y sin un error de
  conexión (RF-4).
- **Dos Administradores reemplazan el modelo a la vez:** queda uno y ningún
  archivo sin dueño (RF-5).
- **Un producto inactivo:** acepta el modelo, como acepta fotos (RF-2).
- **Un nombre de archivo con `../` en la dirección del modelo:** se rechaza
  sin leer nada (400 o 404); la ruta nunca se arma con lo que manda el
  cliente (RF-8).
- **Un error en la base después de guardar el archivo:** el archivo nuevo se
  borra y el anterior queda (RF-5).
- **Un celular sin WebGL:** el visor no puede mostrarlo; se dice y los botones
  siguen sirviendo (RF-9).

## Fuera de alcance

- El visor del detalle para los clientes, el botón «Ver en 3D» y la realidad
  aumentada (HU-16).
- Preparar, comprimir o convertir modelos en la aplicación: se hacen fuera
  (`gltf-transform`, según «Visor 3D y modelos»).
- Más de un modelo por producto, `.gltf` con archivos aparte, USDZ subido a
  mano.
- Un filtro «con o sin modelo» en la lista.

## Criterios de aceptación

Todos los RF con prueba en verde, la revisión de interfaz en escritorio y
celular, y la prueba manual de los escenarios con Docker, incluidos los
modelos de demostración.
